## Codec (`lib/stozher`)

- `stz_crypto`: own SHA-256, HMAC, HKDF and AES-128 (FIPS 180-4, RFC 2104/5869, FIPS 197). No dynamic allocation,
  no platform headers, so the same code runs on the host and the ESP32-S3. A hardware mbedTLS backend can replace
  it behind the same functions later (CLAUDE.md names mbedTLS; the portable code is what is tested now).
- `stz_codec`: `derive_keys`, `encode`, `decode`, hex helpers, jump-code scaling. `decode` checks length, version,
  type, reserved bits and the length/flag agreement, then the tag in constant time, and only then decrypts. On any
  failure the output record is left untouched. Rejection reasons are the API's strings (`reason()`).

## Tests

`make fw-test` (or `pio test -d firmware/node -e native`) builds with `-Wall -Wextra -Werror` and the address and
undefined-behaviour sanitizers, and checks: SHA-256, HMAC (RFC 4231), HKDF (RFC 5869) and AES (FIPS 197) known
answers; every valid golden vector encodes to the same bytes and decodes to the same fields; every invalid vector
is rejected with the stated reason; flipping any single bit of a valid record is rejected.

The vectors reach C++ through `test/test_codec/vectors.h`, generated by `tools/gen_vectors_h.py`
(`make fw-vectors`). `tests/test_firmware_vectors.py` fails if the header is stale, so a new vector in
`tests/vectors/` cannot be missed by the firmware.

`make fw` builds the ESP32-S3 image (a boot self-test that decodes one golden vector and prints the result).

## Second board option: Arduino Leonardo (size probe, Oct 2026)

`pio run -d firmware/node -e leonardo` builds the codec self-test for the ATmega32U4 (28 KB usable flash,
2.5 KB RAM, avr-gcc 7.3 with `-std=gnu++17`). Measured:

| Build | Flash | Static RAM |
|---|---|---|
| Codec (encode, decode, HKDF, AES, HMAC) and the self-test | 9.9 KB (35%) | 941 B (37%) |
| The same plus Ed25519 ack verification (TweetNaCl) | 26.6 KB (93%) | 2867 B (112%) |

Conclusion: the Leonardo can run the record codec, but **not** signed-ack verification; it does not fit even
before the stack is counted. Acknowledgements are optional, so a Leonardo node sends records and retransmits by
policy. The 512 B of SHA/AES tables could move to `PROGMEM` if RAM gets tight. `log2f` is missing in avr-libc,
so the jump-code scaling uses `logf`. The Leonardo's I/O is 5 V: level-shift the lines to the 3.3 V GNSS module
and KIM1 (see CLAUDE.md section 12).

Flashed and run on a real Leonardo (Oct 2026): the self-test decodes golden vector `core_event_jamming` and prints
`STOZHER codec self-test: ok` over USB serial.

## GNSS path and detection (step 3)

`stz_ubx` is a streaming UBX reader (NAV-PVT, NAV-SAT summarised on the fly, NAV-STATUS spoofDetState, MON-RF)
with the CFG-VALSET boot configuration (UBX only, 1 Hz, those four messages; RAM layer, since the module has no
flash). `stz_gnss` assembles one `Epoch` per second from them (by iTOW; a missing NAV-SAT sets `sat_missing`
instead of inventing C/N0). `stz_detect` applies rules J1, S1-S5 and T1 from the specification
(`DetectConfig` holds the initial thresholds), keeps a C/N0 baseline that only follows clean, healthy epochs and
never drifts down with a developing attack, and does not touch any state on `blanked` epochs (own transmitter on).
Event class priority: tamper, spoofing, jamming, time anomaly; the other evidence stays in `Verdict.rules`.
`fill_record` turns a verdict into the telemetry fields of a witness record.

How it is tested: `gen_ubx_vectors.py` builds frames with **pyubx2**, an independent implementation of the u-blox
layouts and key IDs (it corrected one key ID I had from memory: MON-RF output is `0x2091035a`), and the C++ reader
must read the same values back, resync after noise, bad checksums and absurd lengths, and produce a byte-identical
boot configuration frame. The detection tests run **synthetic** recordings (labelled so in the file): ten quiet
minutes with no event, each rule with its time to detect, slow decline not absorbed into the baseline, blanking,
determinism, and a verdict that round-trips through the codec.

Not verified yet: the real module. Layouts come from the pyubx2 tables, which follow the u-blox documentation, but
nothing has been read from an actual M10; `DetectConfig` thresholds are guesses until real captures exist. On the
Leonardo the whole path (reader, epochs, detector, USB report) is 19.7 KB flash (69%) and 1.6 KB static RAM (61%).

## Uplink: KIM1 driver, sequence numbers, retransmission, blanking (step 4)

- `stz_kim1`: builds `AT+TX=<band>,<freq>,<power>,<HEX>\r\n` (band B1-B9, frequency 0-600, or 0-700 for B4/B5, power
  250/500/750/1000/1500 mW, at most 32 data bytes; anything else is refused), and parses `+TX_INFO: 1|0`. The
  hardware seam is `kim1::Port` (UART, TX_STATUS pin), so tests use a scripted modem (`stz_fake_kim1.h`).
- `stz_tx`: never blocks (call `poll()` each loop).
  - **Sequence numbers** are stored *before* use and read back; a failing or lying store means nothing is queued or
    sent. A reboot can only skip numbers, never reuse one. A full queue is detected before a number is taken. Key
    id exhaustion (65535) is refused, not wrapped.
  - **Policy:** a confirmed event goes out at once and repeats twice, 15 minutes apart (different satellite
    passes); a status change goes out once; heartbeats about hourly; unacknowledged entries ride along with the next
    heartbeat at most three times. Failures retry after 60 s, five times, and a silent modem times out after 20 s.
    One transmission in flight, 5 s apart. Events outrank heartbeats; a full queue drops entries already sent first,
    then (for an event) the oldest waiting heartbeat.
  - **Budget:** at most 48 transmissions in a rolling 24 hours (about 1.5 KB); heartbeats stop 12 below that so
    events keep room. The budget lives in RAM, so a reboot forgets it.
  - **Acks:** `on_ack` takes an already verified acknowledgement and applies control.md step 3-5: for this node and
    key, not older than the newest accepted, `max_seq` not going backwards; frees `seq <= max_seq` and the masked ones.
  - **Ack horizon:** at heartbeat time an entry 17 or more behind the newest sequence is freed (`kAckWindow`), the same
    point at which the cloud gives a gap up (`docs/control.md`, distance rule); the mesh queue does it on queueing.
    Queues stay at most 16 (`static_assert`). Left out of the Leonardo build (`STZ_NO_ACK_HORIZON`, no flash left).
  - **Blanking:** `blanked()` is true from the AT+TX command until `+TX_INFO` (or the timeout), while TX_STATUS is
    high, for 3 s after it falls, and after the node's own mesh transmissions. `+TX_INFO: 1` only means the local
    transmission ended; delivery is known only from an acknowledgement.
- `stz_node`: the decision loop without hardware. An epoch gets its `blanked` flag from the uplink, goes through the
  detector, and a new class becomes an Event, the end of one a Status; the heartbeat waits for a first position.
  `src/main.cpp` (ESP32-S3) and `src/leonardo_main.cpp` only add the UARTs, NVS/EEPROM and pins.

Tested on the host with a scripted modem: exact command bytes; bad parameters; reply parsing and garbage; the
sequence rules (restart, crash, failing and lying store, exhaustion); repeats, acks (selective, stale, wrong node),
retries, timeouts, ordering, budget, queue pressure; blanking including the case where the receiver is really upset
by our own burst (the detector stays quiet with the flag and raises a false jamming event without it); and the
whole path from epochs to `AT+TX`.

**Unverified against a real KIM1** (assumptions to check on the module): CR LF as the line end; that the reply is
exactly `+TX_INFO: 1` / `+TX_INFO: 0`; how long a transmission takes (the fake uses 1.5 s); whether TX_STATUS rises
before or after the command is accepted; the band and frequency (placeholders `B1`, 300, 500 mW until the
organisers give the real values). The pin numbers in both mains are placeholders.

Leonardo: with the whole node (UBX, detection, uplink, EEPROM store, software serial) the image is 27.9 KB of the
28.7 KB flash (97%) and 1.5 KB static RAM (59%, queue of 4). It fits but there is no headroom left there; the
ESP32-S3 image is 299 KB (9%).

## Mesh uplink (step 5)

The witness node talks to a **stock Meshtastic** T-Beam through that device's Serial module in TEXTMSG mode, as
the specification says (we write no mesh firmware, `docs/mesh.md`). `stz_mesh`:

- **Out:** every record the uplink queues is also sent as `STZ1:` + lowercase hex + newline (the Serial module
  sends one message per line). The text equals `"STZ1:"` + the golden vector hex for all valid vectors. An event
  goes out at once and once more after 30 s; status changes and heartbeats once; messages are at least 5 s apart
  and capped at 40 an hour, because LoRa airtime is shared. A write that fails is retried, never waited for.
  The gateway and the API already drop mesh repeats (same sender, same bytes).
- **Back:** lines from the Serial module are read; only a line that is `STZA1:` + a valid cloud signature (the
  same verification as for any ack, `stz_ack`) counts. Chat, other apps, half lines, over-long lines and forged
  acks are ignored. A verified ack goes to `Tx::on_ack`, which frees the satellite queue and the mesh queue
  together.
- **Blanking:** each mesh send tells the uplink (`note_mesh_tx`, 2 s of airtime plus the guard) so the detector
  does not read our own LoRa burst as an attack. This is approximate: the Serial module forwards the text when its
  radio gets a slot, which we cannot see.
- **Optional by construction:** `Node` takes a mesh link or none; without one the node is the satellite-only
  node, and the record's "mesh present" flag says which. `STZ_NO_MESH` leaves the code out of the image (the
  Leonardo build, which has 22 bytes... no room: 97.8% of flash without it) and `STZ_NO_ACK_VERIFY` drops ack
  verification on boards that cannot hold it.
- **ESP32 wiring (placeholder pins):** UART0 on D6/D7 to the T-Beam, 38400 baud (must match `serial.baud`
  there), GNSS on D9/D10, KIM1 on D8/D0 with TX_STATUS on D1, I2C D4/D5 left for the Grove sensors.

Not verified: the T-Beam side. Its Serial module needs `enabled`, `mode = TEXTMSG`, matching `baud` and the
`rxd`/`txd` pins set (check the names and values against the Meshtastic documentation or the app), and I have not
confirmed that, in that mode, a *direct* message addressed to the node is written to the serial port the way a
channel message is. If it is not, acks will not arrive over this path and the satellite-only retransmission
policy still works. The node cannot probe the Serial module at boot (it has no handshake), so "mesh present" comes
from configuration, not detection.

## T-Beam fork: STOZHER inside Meshtastic (analysis and step 2)

**Why.** The T-Beam is an ESP32 running Meshtastic; a STOZHER module inside that firmware would replace the
XIAO node, the serial link and the second device. From reading the Meshtastic source (2.8.x, `Meshtastic-firmware`):
a module can send and receive text packets in process (`allocDataPacket`, `sendToMesh`, `handleReceived`), so the
`STZ1:` uplink and the `STZA1:` acks need no Serial module; `RadioTxHook` reports when the radio starts and finishes a
packet, which is exact blanking instead of a guess; and `GPS::whileActive()` reads every GPS byte, so one line there
taps the stream. `lib/stozher` has no Arduino dependency and is used as is.

**Costs.** The NEO-6M is GPS-only with no spoofing flag (rule S3 cannot fire) and speaks the older dialect (NAV-SVINFO
and MON-HW instead of NAV-SAT and MON-RF; now supported by `stz_ubx`, vectors from pyubx2). Meshtastic duty-cycles the
GPS (your boards: `gpsUpdateInterval` 120), which detection cannot live with. The KIM1 needs a UART and a status pin
on a board with few free pins. The firmware is GPL-3.0, so the T-Beam image is too (declared in DECLARATIONS.md);
that is why the integration is a patch plus a few files, not a vendored copy. It cuts against the "we do not write
mesh firmware" line of docs/mesh.md, so the XIAO design stays as the fallback.

**Size.** Stock `tbeam` 2.8.2: 2,057,744 bytes in a 2,424,832-byte app partition. With the tap: 2,060,688 bytes (+2.9 KB),
85.0% of the partition, 110 KB static RAM. Our whole node logic is about 60 KB, so there is room.

**Step 2 (this commit).** `firmware/tbeam/`: the tap, a patch and an apply script; `tbeam-stozher` builds. It only
logs one line per second (`STOZHER epoch tracked=... cn0=... jam_ind=...`) and the first MON-HW. NOT flashed yet. The
MON-HW length (60 or 68 bytes) and whether the NEO-6M in the T-Beam sends NAV-SVINFO at all are exactly what the first
flash is meant to show. The 68-byte MON-HW test vector is hand-made, not from pyubx2.

Next (in order): flash one board and read real data; always-on GPS configuration; the module that sends `STZ1:` and
receives acks; the KIM1 on UART2.

**First flash (Oct 2026, T-Beam "abac").** Backed up the whole 4 MB flash first (`data/tbeam-backups/`, git-ignored,
it holds the board's keys), then flashed `tbeam-stozher` over USB (all partitions verified by hash). Real data from the
NEO-6M, read from the debug log:

- Meshtastic identifies it as **u-blox 6, firmware 7.03, hardware 00040007**. Both new messages arrive **once a second
  with no checksum errors** (20 NAV-SVINFO and 20 MON-HW in the first 30 s, 0 bad).
- Indoors by a window: 7 to 11 satellites tracked, 5 to 8 used, mean C/N0 about 20 dB-Hz, spread 3 to 7 dB, `jam_ind`
  3 to 4, noise 99, AGC 6630, `jam_state` 1 (ok). That is the first real "normal" baseline; it is a poor-sky one.
- **GPS duty cycling is real**: with Meshtastic's default `position.gps_update_interval` (120 s) the receiver was
  powered down about 20 s after the fix. Setting it to **5 s** (anything at or under 10 s keeps the GPS on, per
  `GPS_UPDATE_ALWAYS_ON_THRESHOLD_MS`) gave one epoch per second continuously (70 in 70 s). This setting was changed on "abac".
- Still unknown: whether MON-HW is the 60- or 68-byte form (values look sane either way; log the length next), and
  whether `jam_state` ever leaves 1 on this receiver (it is the M8-style field; the NEO-6 may only use `jam_ind`).

**Step 3 result (Oct 2026, over real LoRa).** The STOZHER module (`firmware/tbeam/src/StozherModule.*`) runs the same
node logic as the XIAO build inside the T-Beam firmware: epochs from the GPS tap -> detector -> `STZ1:` broadcasts
through `sendToMesh`, `STZA1:` acks taken from incoming text packets in process, every radio transmission (a
`RadioTxHook`) blanking the detector. No KIM1 here: `TxConfig::satellite_enabled = false`. Node id and key are
build-time values (`STOZHER_NODE_ID`; the PUBLIC test key), the boot log says so.

With node 4242 registered (mesh transport id of the board), the other T-Beam as gateway and `mesh_bridge` + API on the
laptop, three records arrived as `received_via: mesh`: a scripted self-test episode (`STOZHER_SELFTEST_AT_S=150`,
synthetic epochs, so the records are **type `test`**, confidence 18, then the end-of-event status) and a live heartbeat
(type `heartbeat`, real position). Bridge counters: 3 accepted. The bridge also fetched and sent a signed ack.

Found on the way:
- **The Meshtastic node number changed with the 2.7.26 -> 2.8.2 upgrade** (`!bdf0abac` became `!5faa5e2e`, device state
  version 24 -> 25). The backend had to learn the new transport id (done in the dev DB by hand: there is no way to change
  a node's transport id through the API, which a replaced or re-flashed radio needs; open item).
- **The ack, first try, did not arrive** with the boards side by side: `Ignore rx packet, error=-7` (RadioLib's CRC
  mismatch) at RSSI about -52 dBm and TX power 27 dBm, which points at receiver overload at close range.
- **The ack, second try, arrived** once the gateway board was moved away: the node logged `ack text from !bdf0a4b0 queued
  for verification` and then `signed acknowledgement verified and applied`. So the whole loop has now been seen on air
  between two real T-Beams: record -> LoRa -> gateway -> `mesh_bridge` -> API -> cloud-signed ack -> LoRa direct message ->
  module -> Ed25519 verification (TweetNaCl) -> applied. Even then several direct messages still failed the CRC
  (RSSI still strong), and the bridge's link-layer retries are what got one through. Bridge counters over the run: 6 records
  accepted, 0 rejected, 3 acks sent.
- **Port names move.** Moving a board re-enumerated both: `ttyUSB0` became the other board, and a bridge started with
  `--port /dev/ttyUSB0` then reconnected to the wrong radio. Use `/dev/serial/by-id/...` paths. A serial client that
  connects to a board leaves it in protobuf mode (binary frames instead of the text log) until it reboots.

**KIM1 in the T-Beam fork (Oct 2026).** `-DSTOZHER_KIM1=1` adds `Uart2Kim1` (UART2, 4800 8N1, TX_STATUS on a pin with an
internal pull-down, so an unplugged KIM1 reads "idle") and turns the satellite path on in the same library that the XIAO
build uses: sequence numbers, repeats, daily budget, retries, blanking while TX_STATUS is high plus a guard, `+TX_INFO`
handling. Both flavours build (default 2,082,799 bytes, with KIM1 2,083,335, 85.9% of the partition). What is NOT done:
no KIM1 has been connected, so the exchange with the real module is untested (see the assumptions listed under step 4);
the default pins 36 / 14 / 25 were picked from the Meshtastic variant file and **not verified against the T-Beam**
(I could not find a trustworthy header pinout), and I have deliberately not flashed this flavour to "abac" with nothing
wired, because driving a pin that turns out to be connected to something on the board is a risk with no benefit.
Before wiring: confirm each pin is broken out and free on the board in hand.

**First run through the whole stack with real hardware (Oct 2026): two false alarms found and fixed.** With the worker and
dashboard running, "abac" showed up as a live node, and the dashboard drew a jamming hotspot and a degraded trust area
at the board's position ("1 witness, 1 report"). The cause was real, not simulated: right after a boot the NEO-6M
reports `jammingState` 2 (warning) and steps its clock when it first gets a fix, so the node raised a `jamming` event
(receiver flag, confidence 18) and a `time_anomaly` event (confidence 12) a few seconds after boot. Fixes in
`stz_detect`: a **start-up holdoff** (`startup_holdoff_epochs`, 30 s) during which the receiver's own jamming and
spoofing flags and clock steps are not judged (a node that boots under real jamming still reports it about 30 s
later), and **GNSS time only counts as a reference while there is a fix**. Three new host tests cover this
(a cold receiver warning and stepping its clock stays quiet, a flag that persists past the holdoff is reported, time
without a fix is ignored). The `type: test` self-test records are, correctly, not analysed by the worker.

**Bluetooth crash on the test board (Oct 2026).** abac rebooted several times a few seconds after boot: the log showed `ASSERT_ERR(0), in ld_acl.c` and a Guru Meditation (IllegalInstruction) right after Bluetooth advertising started. The cause is not proven (the Meshtastic 2.8.2 Bluetooth stack, or a bonded device reconnecting). The board was rebuilt with `-DMESHTASTIC_EXCLUDE_BLUETOOTH=1`. A first guess, that the serial API refused requests because `security.serial_enabled` was off, was wrong: the log itself is gated by the same setting and was printing. The serial CLI answered again after the reflash. Note that opening a board's serial port can reset it.

**USB noise swamps the T-Beam's GPS (Oct 2026).** On the test board, the receiver tracked 6-9 satellites by a window on battery, but with the USB cable plugged into the laptop it often tracked 0-2 and reported `jam_state=3` (critical); the satellites came back within minutes of unplugging the cable. The detector flagged this correctly as local interference (class jamming, from the receiver's own flag and C/N0 drops), and the jamming/normal flapping we saw at the window while plugged in is most likely the same noise. Consequences: (1) test the detector on battery, or on a power bank, and read the result from the database, not the serial log; (2) a field witness needs distance from laptops and USB hubs, a short shielded cable or ferrite, and the antenna kept away from the board's own electronics (this is one reason the expert node uses an external GNSS antenna); (3) a first-boot receiver flag and an indoor GPS-only board are not representative of the M10 expert node, so the rule thresholds (`cn0_drop_db` 6, 3 epochs) are not tuned yet. The per-epoch log (`STOZHER_EPOCH_LOG_S`) is how the numbers are collected when the board is on USB.

**Hysteresis in rule J1 (Oct 2026).** A foil cover on the test board cut the signal by about 8-10 dB, which sat on the 6 dB trigger level, and the node sent eight start/stop records in six minutes. Each status change is a satellite message (budget about 48 a day), so a signal hovering at the threshold must give one event. Two changes in `stz_detect`: (1) once J1 is active the drop must fall below `cn0_clear_db` (3 dB) for `clear_epochs` before it ends, instead of the 6 dB trigger level; (2) every event is held at least `min_event_ms` (30 s). Three host tests cover it (hovering signal gives one event; held above the clear level; a short event is held). The thresholds are still the synthetic defaults, not tuned on real data. The Leonardo image is now 28532 of 28672 bytes (99.5%): there is almost no room left on it.

**J1 per satellite and corroboration (Oct 2026).** The first real runs on the T-Beam showed J1 firing on nothing: two "jamming" events in 17 minutes with the window open (mean C/N0 23 down to 19, receiver flag clear, AGC flat), and a foil cover that stayed under the trigger. Cause: J1 used one feature, the mean C/N0 against a slow mean baseline, and the mean moves when the set of tracked satellites changes. Two changes, guided by the indicator-combination idea in Crespo et al. (GMV, Eng. Proc. 126, 8, 2026; three levels nominal / off-nominal / anomaly, no single metric decides): (1) the drop is the median over the satellites seen now and in the baseline of (their own baseline - now), kept per satellite in a 24-entry table (`ubx::SatSummary` and `Epoch` carry `sv_key`/`sv_cno`; key = gnssId<<8 | svId); with fewer than `min_sv_match` (3) matches it falls back to the mean drop; (2) an event starts on a drop between `cn0_drop_db` (6) and `cn0_drop_strong_db` (12) only if a second sign agrees: the receiver warns, the fix is lost, `sat_loss` (2) tracked satellites are missing against their baseline, or the jamming indicator is `jam_ind_rise` (10) above its baseline. A drop of 12 dB or more stands alone. Without a second sign the node stays quiet and `Detector::suspect()` is set (local only, not transmitted). Once active, the existing hysteresis applies unchanged. Six new host tests (118 in all). The thresholds are still synthetic: the epoch log (`STOZHER_EPOCH_LOG_S`) now also prints one `STOZHER sv:` line with each satellite's id and C/N0, to calibrate on a quiet session and a metal-tin cover session. The Leonardo build defines `STZ_NO_PER_SV` and keeps the old mean-based rule (28586 of 28672 bytes). The ML/DL paper (Ghanbarzadeh et al., arXiv 2501.02352) needs raw IQ or per-satellite pseudorange and Doppler sets and large labelled data; not usable on the node, kept as background for the worker-side classifier.

**Loss of reception is not jamming (detector rev 4, Oct 2026).** A metal tin over the GPS patch of the T-Beam gave a 12 dB drop with the C/N0 spread falling to 3 dB, and the node called it jamming (seq 148). The receiver's jamming indicator (MON-HW `jamInd`) stayed at its normal 2-3 and its own flag stayed off: the noise floor did not move. Jamming raises the noise floor; a cover, a tunnel or a building lowers the signals and leaves it alone. The platform already expects this distinction (`docs/scenario.md`: benign if C/N0 drops but AGC stays low; `docs/trust.md`: class 3 argues for DEGRADED; the worker makes no hotspot for it), so only the node rule was out of line. Changes in `stz_detect`: (1) **noise evidence** = the receiver's jamming state >= 2, or `jamInd` at least `jam_ind_rise` (10) above its slow baseline, or `noisePerMS` at least `noise_rise` (40, not calibrated yet) above its baseline; `Epoch` now carries `noise` and `agc`, and the epoch log prints them. (2) **J1 (jamming)** needs the C/N0 drop plus noise evidence, or the receiver flag alone as before; the stand-alone "large drop" path and the satellite-loss sign are gone (losing satellites is what a cover does). Once raised, an event is held by the existing clear level whatever the noise says. (3) **L1 (loss of reception, rule bit 7)**: the same drop without noise evidence for `loss_epochs` (60 s) is class 3, benign degradation, confidence 6 plus up to 4 for duration, and never above jamming's. If noise evidence appears later the class rises to jamming (a second record). Class priority: tamper, spoofing, jamming, time anomaly, benign, normal. (4) A heartbeat sent during an event now repeats the event's confidence and drop (it used to say jamming with confidence 0 and drop 0). Host tests (124 in all) cover: a drop without noise is class 3 after a minute and never jamming, a large drop without noise is still class 3, a dip under a minute sends nothing, a loss becomes jamming when the noise rises, the noise level alone is evidence, a cover replay clears when the satellites return, and the worker keeps a class 3 report as a degraded cell with no hotspot. **Limit:** a real jamming signature (noise indicator up) cannot be produced on our hardware, because we never transmit; it is covered by host tests and by the self-test, which injects the receiver flag. The thresholds, especially `noise_rise`, are synthetic until calibrated on real data. The Leonardo build (`STZ_NO_PER_SV`) keeps the old mean-based rule without loss-of-reception, and now fits in 28638 of 28672 bytes (34 bytes spare).

**Receiver recovery (detector rev 5, Oct 2026).** After a 30-minute metal-tin cover on the T-Beam, the NEO-6M did not find satellites again for 13 minutes and the board had to be reset by hand; no event cleared in that time, which is correct for the rule (no signal) but useless in the field. `stz_recover` (`ReceiverWatch`, pure logic) asks for a restart of the receiver's GNSS engine when there has been **no fix for 300 s while the band is clean** (`Detector::band_clean`: no noise evidence and no jamming event active). Restarting during real jamming only throws state away, so it never fires then. Restarts are spaced 10 minutes for the first three, then hourly, so a node indoors with no sky does not restart all day; a fix resets the count. `Node::take_receiver_restart()` hands the request to the board code and has already called `Detector::receiver_restarted()`, which restarts the start-up holdoff and the continuity checks (a cold receiver warns about spoofing and steps its clock while it acquires: a host test shows that without the notice this raises an event, and with it nothing does). On the T-Beam, `StozherModule` sends UBX-CFG-RST (`navBbrMask` 0x0000 = hot start, `resetMode` 0x02 = controlled software reset of the GNSS only) through `GPS::stozherWriteRaw` (patch `0002-stozher-gps-restart.patch`, a raw-write hook in the Meshtastic GPS class) and, two seconds later, asks for NAV-SVINFO and MON-HW again in case the restart cleared them. The frames are checked byte for byte against pyubx2. **Not verified on the receiver:** the `resetMode` values come from community driver documentation (ROS `ublox_msgs` CfgRST, a Zephyr driver) and not from the u-blox 6 manual, which was not available here; confirm on abac that the receiver keeps sending the two messages after the restart (the re-enable call is the fallback) and that it then finds satellites. Host tests (135 in all): restart after 300 s of no fix with a clean band, never in a noisy band, never with a fix, timer reset by a fix or a noisy band, spacing and the hourly slowdown, the try count reset by a fix, the node asks once, and a cold receiver raises no event after the notice. The Leonardo build excludes all of it (`STZ_NO_PER_SV`); its image is 28638 of 28672 bytes.
