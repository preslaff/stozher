# Signed control traffic (v1): acknowledgements

Control traffic flows from the cloud to nodes and field kits, so it must be unforgeable: a rogue
node must not be able to make others delete evidence. Everything here is signed with the cloud's
Ed25519 key; anything unsigned, malformed, or signed by an unknown key is **ignored**
(CLAUDE.md, signed control traffic). Acknowledgements are the first message type; mesh summaries
and node commands will use the same signing rules with their own type byte and context string.

## Cloud signing key

Ed25519. The private seed (32 bytes) is provisioned only through the environment
(`STOZHER_ED25519_SEED`, hex; never logged or returned). A one-byte **cloud key id** lets the key
be rotated: nodes and field kits hold the public keys they trust, by id. The public key is served
unauthenticated at `GET /v1/control/public-key` for provisioning; trust it only through a channel
you control (flash it at installation), not at runtime.

## Acknowledgement

An ack tells one node which of its records the cloud holds, so it can drop them and skip
retransmitting. For a node and a key id, with sequence numbers starting at 1 under each key:

- `max_seq`: the highest sequence number N such that **every** sequence 1..N was received
  (highest contiguous, as in the specification). 0 if sequence 1 has not arrived.
- `mask` (uint16): selective acknowledgement beyond the gap. Bit i (i = 0..15, least significant
  first) is set when sequence `max_seq + 2 + i` was received. (`max_seq + 1` is by definition
  missing, so it needs no bit.) A node may drop records marked in the mask and must keep
  retransmitting the missing ones in between.
- `signed_at`: cloud Unix time in seconds when this ack was signed.

Sequence numbers do not wrap under one key: rotate the key id before 65535 (docs/packet.md).

### Message layout (15-byte payload + 64-byte signature = 79 bytes)

| Bytes | Field |
|---|---|
| 0 | type and version: `0xA1` (acknowledgement, version 1) |
| 1 | cloud key id |
| 2–5 | node id, uint32 big-endian (the same node id as in docs/packet.md) |
| 6 | node key id |
| 7–8 | `max_seq`, uint16 |
| 9–10 | `mask`, uint16 |
| 11–14 | `signed_at`, uint32 |
| 15–78 | Ed25519 signature |

`signature = Ed25519-Sign(sk, "stozher/v1/ack" ‖ payload)` where `payload` is bytes 0–14. The
context string separates acknowledgements from every other signed message type. Ed25519 is
deterministic, so a given payload and key always produce the same 79 bytes.

### Wire form

Hex of the 79 bytes (158 characters). On the Meshtastic mesh: `STZA1:` + hex (164 characters),
sent as a direct message to the node (record text is `STZ1:`, see docs/mesh.md).

### Receive rules (node, field kit, gateway)

1. Prefix, hex and length (79 bytes) valid; type byte `0xA1`; otherwise ignore.
2. The cloud key id is one the receiver trusts; the signature verifies. Otherwise ignore.
3. The node id is the receiver's own (nodes) and the node key id is a current key.
4. Freshness: `signed_at` must not be older than the newest ack already accepted for this node
   and key, and `max_seq` must not go backwards. Equal values are harmless repeats. (A node's own
   clock may be wrong, so freshness is relative to previously accepted acks, not wall time.)
5. Then drop stored records with `seq <= max_seq` and those marked in `mask`; keep retransmitting
   the rest by policy.

Rejection reasons used by the reference code (`stozher_core.control`): `bad_text`, `bad_hex`,
`bad_length`, `bad_type`, `unknown_cloud_key`, `bad_signature`.

### Golden vectors

`tests/vectors/ack_messages.json`, generated by `tests/vectors/make_ack_vectors.py`, which signs
with the `openssl` CLI independently of `stozher_core`. The test seed is public and must never be
used outside tests. Every implementation (Python, C++) must verify the valid vectors, produce the
same bytes for the same fields, and reject the invalid ones with the stated reason.

## Proposed: giving up on old gaps (not built, team decision)

**Status: proposal.** Nothing below is implemented; today `max_seq` is strictly "every sequence 1..N was received".

**Problem.** One record that never arrives pins `max_seq`. The mask reaches 16 further, so every later record beyond
that window is never acknowledged, however many the cloud holds. Observed: a T-Beam whose sequence 1 never arrived
has received the same ack (`max_seq` 0, mask full, covering 2 to 17) since 15 October 2026 while more than 250 records
arrived. On the mesh path this costs only airtime (the node does not keep records). On the satellite path a node resends
an unacknowledged record at most `max_resends` = 3 times at heartbeat time (`firmware/node/lib/stozher/stz_tx.h`), so the
cost is up to three wasted transmissions per record, from a small daily budget, not a stuck queue. A mesh retransmission
(`docs/decentralised-mesh.md`, step 3) would add the same cost there.

**Rule.** A missing sequence `s` counts as *given up* once the cloud has held a later record (sequence greater than `s`)
for at least `give_up_after` (proposed 6 h: longer than three heartbeat-time resends at the default 3600 s interval;
configurable per deployment). Then:

- `max_seq`: the highest N such that every sequence 1..N was received **or given up**.
- `mask`: as today, computed above that `max_seq`.

**Properties.**

- No wire, golden-vector or firmware change: nodes already drop `seq <= max_seq` (receive rule 5).
- `max_seq` never goes backwards: gaps only age into given up, and a late arrival only fills one.
- A late arrival is still ingested and stored normally; giving up concerns the ack only.
- Loss stays visible: `missing` in `GET /v1/nodes` still counts given-up sequences.
- Deterministic from the held sequence numbers, their arrival times and the signing time, so two signers holding the
  same records sign the same `max_seq` once both windows have passed.
- Cost: a node may drop a record the cloud never received, but only after it had `give_up_after` to resend it.

**Tests to write once agreed** (`stozher_core.control`, pure function; API test through `GET /v1/acks`):

| Held | Arrival of the later records | Expected `max_seq` |
|---|---|---|
| 2..30 (1 missing) | 1 h ago | 0 (window not passed; mask 2..17 as today) |
| 2..30 (1 missing) | 7 h ago | 30 |
| 1..5, 7..9 (6 missing), then 6 arrives late | 7 h ago | 9, and later signatures never lower it |
| 1..3, 5..10 (4 missing, old), 12..14 (11 missing, recent) | 7 h ago / 1 h ago | 10, mask covers 12..14 |
| simulated node | any | same rule, ack labelled `sim` as today |

**Decisions needed:** adopt or not; the value of `give_up_after`; whether it is one deployment-wide setting or per node
kind (satellite nodes resend for longer than mesh nodes).

## Delivery

`GET /v1/acks` (system role) returns the latest signed ack for a node; see docs/api.md. The mesh
bridge fetches it after forwarding records from a node and sends it back as `STZA1:` text, rate
limited per node. Satellite nodes have no downlink, so acks reach them only through a gateway.

## Seeing delivery status

`GET /v1/nodes` (operator) reports, per node, what the cloud holds and whether the newest signed ack covers it (`delivery.ack_current`), so an operator can tell
a silent node from one that is delivering but has not been told yet. It cannot tell what a node sent and the cloud never received: gaps (`missing`) are only
visible below the highest sequence number held. Acks are signed on request by the bridge, so `ack_current: false` for a moment after new records is normal;
it stays `false` when no gateway hears the node (a satellite-only node never receives acks).

An ack reaches at most 16 sequence numbers beyond its contiguous run, so one record that never arrives keeps every later one
unacknowledged even though the cloud holds them, and the ack stays the same: `ack_current` is then `true` while `unacked`
(records held that the newest ack does not cover) grows and `acked_through` (the highest sequence it covers) stays put.
Seen on a T-Beam whose sequence 1 never arrived: `acked_through` 17 for a week. See "Proposed: giving up on old gaps" above.

See also `docs/decentralised-mesh.md` (proposal, not built), step 4: more than one ack signer.
